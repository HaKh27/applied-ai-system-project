# Model Card: PawPal+ AI Care-Gap Suggestions

This documents the one AI feature in PawPal+ — the care-gap suggestion agent in `care_ai.py` — and the responsible-AI reflection for this project. See [`README.md`](README.md) for the full project writeup, architecture, and sample interactions; this file covers the model/system details and the graded reflection specifically.

## Overview

- **What it does:** compares a pet's existing tasks against a small species care-guideline knowledge base, and drafts a concrete missing task (e.g. an evening feeding, a vet checkup) grounded in that guideline text for a human to approve or reject.
- **Model used:** Claude Haiku 4.5 (`claude-haiku-4-5-20251001`) via the Anthropic Messages API, called from `care_ai.AnthropicClaudeClient`.
- **Where it sits in the system:** one step in a larger pipeline — a deterministic retriever and gap detector run before it (no AI), and a deterministic de-conflict pass and a mandatory human approval gate run after it (also no AI). The model is never the last step before something becomes real.

## Intended Use

PawPal+ is a course project / portfolio demo, not a production pet-care product. The AI suggestions are meant to catch obvious gaps in a care routine (e.g. "this dog has no walk scheduled") and are grounded only in a handful of hand-written, illustrative guideline sentences — **not veterinary advice**, not comprehensive, and not reviewed by a veterinarian. It should not be relied on for an actual pet's real medical or care needs. The human-approval requirement exists precisely because the system is not trusted to make care decisions unsupervised.

## Responsible AI Reflection

### What are the limitations or biases in your system?

**Limitations:**

- **The guideline corpus is small, hand-written, and not vetted.** It covers a handful of categories for dog and cat plus a generic fallback for everything else — it is illustrative, not authoritative, and should never substitute for real veterinary guidance.
- **Gap detection is keyword-based, not semantic.** `detect_gaps` looks for substrings like "walk" or "feed" in a task's name. A task phrased unusually (e.g. "give Rex a stroll") could be missed and falsely flagged as a gap; conversely an unrelated task that happens to contain a keyword could falsely count as coverage.
- **Species matching is exact-string, case-insensitive.** A typo or an unusual spelling (e.g. "doggo") silently falls through to the generic fallback guidelines rather than erroring or warning the user that a more specific match wasn't found.
- **The AI doesn't see the whole day when it drafts a time.** Each category is drafted independently; the de-conflict pass fixes exact collisions between a pet's own suggestions and its existing tasks, but it doesn't optimize placement, and a drafted time can still fall outside the owner's available window — in which case the real scheduler will silently drop it from today's plan the next time it runs, which could be confusing if a user doesn't notice why an approved task isn't showing up.
- **No persistence.** All data — pets, tasks, dismissed suggestions — lives in Streamlit's in-memory session state and is lost on a server restart. There's no database, no multi-device sync, and no authentication; this is a single-user local demo.
- **Hard dependency on a third-party paid API.** The feature is entirely unavailable if `ANTHROPIC_API_KEY` is unset, the account lacks billing, or the service is unreachable. This is handled gracefully (the app degrades to its non-AI functionality with an explanatory caption rather than erroring), but it does mean the feature's availability is outside this project's control.
- **No evaluation against real users or real pets.** Reliability testing (see `tests/test_ai_suggestions.py`) checks the agent's logic — retries, grounding, validity, de-conflicting — against a fake client, not against how well its suggestions actually match what a real pet owner would want.

**Biases:**

- **Species coverage is uneven by construction.** Only dog and cat get tailored categories (walk, litter, grooming, etc.); every other species — rabbits, birds, reptiles, anything someone types into the "other" field — gets the same generic fallback. A less common pet systematically gets less useful, less specific suggestions, not because the AI reasoned about that species, but because nobody wrote guidelines for it.
- **The corpus reflects one person's (my) assumptions about "typical" pet care** — e.g. "dogs are fed two meals a day" — written without veterinary review or any check against how care norms vary by owner, culture, or region. Anyone whose actual routine doesn't match those defaults will get suggestions skewed toward an assumed norm rather than their situation.
- **Whatever biases exist in Claude's own training data about pet care carry through un-audited.** I didn't evaluate the model's output for this beyond checking that it stayed grounded in the guideline text I gave it — grounding prevents invented facts, but it doesn't prevent the model from framing a correct fact in a skewed way.

### Could your AI be misused, and how would you prevent that?

The most realistic misuse isn't malicious — it's **over-trust**: someone treating a drafted suggestion as real veterinary guidance for an actual sick or injured pet. The guideline corpus is explicitly not vetted (see above), so acting on it for a real medical situation could cause real harm through neglect of actual care. Prevention: the "not veterinary advice" disclaimer in Intended Use above, and structurally, the human-approval gate means nothing reaches a real schedule without a person reading and accepting it first — but that only helps if the person is actually reading it critically rather than reflexively clicking Keep.

The more technical risk is **prompt injection**: `pet.name`, `pet.species`, and every existing task's name are interpolated directly into the prompt sent to Claude with no sanitization (see `care_ai._build_prompt`). Someone could name a pet or a task something adversarial, aimed at making the model ignore its instructions or produce unexpected output. I didn't add input sanitization against this. What limits the damage instead is that the model's only real capability is proposing a `Task` — name, time, duration, priority, frequency — and every proposal still has to pass the same validation as a manually-typed task and still needs an explicit human Keep before it does anything. Even a successfully "hijacked" draft can't do more than a weird-looking task suggestion that a human can reject.

A smaller risk: **cost abuse**. Nothing stops a user from clicking "Generate schedule" repeatedly to rack up API calls against whoever's key is configured. Haiku 4.5 keeps each call cheap and the pending-suggestion de-duplication (`generate_suggestions`'s `pending` filter) avoids redundant re-drafting of the same gap, but there's no rate limit, and I didn't build one.

### What surprised you while testing your AI's reliability?

The biggest surprise wasn't in the AI's output at all — it was in my own verification process. Claude Code once told me a potential collision bug was "verified, no bug" based on a reproduction it had constructed itself with invented data, rather than the exact real scenario. I pushed back after seeing a live screenshot that still looked wrong, and it turned out the real cause was a stale Streamlit process still running an old, cached copy of `care_ai.py` — Streamlit reruns `app.py`'s own code on every click, but Python only imports a module once per process, so an edited module silently keeps running old logic until the whole server is restarted. Once we restarted cleanly and re-ran the identical scenario, the real `pawpal.log` showed the de-conflict logic working exactly as designed (drafted at 10:00, nudged to 11:00 in the same second). The lesson: a confident-sounding "I checked, it's fine" is only as good as whether it checked the *actual* running system, not a plausible stand-in for it.

The second surprise was more about the AI feature itself: **individually correct suggestions could still be collectively wrong**. Each drafted task passed its own validation and was grounded in a real guideline — nothing wrong with any single one — but because each category is drafted by an independent model call with no visibility into the others, two suggestions for the same pet could land on the exact same time. No per-suggestion check would ever catch that; it only became visible by looking at the whole batch together, which is exactly the kind of thing schema validation can't do and a human (or a dedicated aggregate check) has to.

### Describe your collaboration with AI during this project

This entire feature was built in close collaboration with Claude Code, working iteratively rather than as a single handoff. The AI feature itself went through a real design negotiation before any code was written: Claude Code first proposed natural-language task entry as the AI feature, and I pushed back on it by raising edge cases it hadn't accounted for — what happens when the referenced pet doesn't exist yet ("take Max on a walk" when there's no pet named Max), what happens when a pet is literally named after its own species ("Dog" the cat), and what happens when two pets' names and species are swapped. Working through those cases with Claude Code made it clear that free-text pet resolution was fundamentally ambiguous in ways that would be hard to fully close off, so I proposed pivoting the whole feature instead: an AI agent that looks at the schedule and suggests what's missing, with the human approving or rejecting each suggestion — a design that sidesteps that entire class of ambiguity, since it never has to parse a free-text reference to a pet at all. From there, Claude Code used plan mode to write up a concrete implementation plan (data flow, function signatures, file-by-file changes) for that direction before touching any code, which I reviewed and approved before implementation started.

**A suggestion I accepted:** Claude Code recommended using Claude Haiku 4.5 (not a larger model) to draft suggestions, reasoning that drafting one short, grounded JSON object per care gap doesn't benefit from a bigger model and that keeping each call cheap mattered since a single "Generate schedule" click can fire off several drafts at once. I didn't push back on this — it became part of the implementation plan I reviewed and approved before any code was written. In hindsight it's exactly the kind of model-sizing judgment call that's easy to get wrong in either direction (too small to follow instructions reliably, or needlessly expensive), and the reasoning was specific to what the task actually required rather than a generic "use the best model" default.

**A suggestion I did not accept as written:** Claude Code's first UI for AI suggestions rendered each pending suggestion as its own box with a full set of editable fields inside — not wrong, exactly, just more complicated than I wanted. It took a couple of rounds to land on what I actually meant: approved tasks highlighted green, pending ones highlighted red, laid out as simple rows a human can scan and decide on at a glance, not a separate section with editable forms. Once that landed, Claude Code rebuilt the suggestions as color-coded rows in the same table as the regular schedule — simpler to look at and simpler code, since there was no longer any per-field form state to track. This is the "simplified/scoped down" case rather than "wrong": the original design worked, it just wasn't the right fit for how I wanted to use it.
